# 切換與回復流程

在可安排停寫的維護窗口中，依序準備目標環境、控制寫入、搬移資料、驗證並開放服務。先確認以下條件，再把各階段的動作、成功證據與失敗處置填入切換計畫。

## 先決定能否使用這個流程

| 條件 | 處理方式 |
| --- | --- |
| 能安排停寫，資料搬移與驗證能在窗口內完成 | 可用以下關卡審閱計畫，具體步驟、耗時與失敗處置仍依環境驗證 |
| 資料量讓完整搬移超出窗口 | 評估預先複製與最後增量同步，確認同步邊界後再修訂計畫 |
| 需要持續複寫、分批流量或跨地多寫 | 超出本流程範圍，需另行設計一致性、同步位置與衝突處理 |
| 外部事件無法暫停 | 查明保留與重送能力、去重方式及對帳機制；未處理前不把來源視為可安全停寫 |

## 準備階段

先列出所有狀態：資料庫、物件或附件、待執行工作、排程、外部系統已接受的操作。對每一種決定搬移、共用、重建或保留的方式，並標明相互一致的條件。

核對執行版本與部署方式，確認目標環境可承接必要功能。不要把搬家、功能更新與架構重建混成一項未經評估的變更。

先做隔離還原與功能預演。確認對外連線、通知與背景執行受控，記錄耗時、資料比對範圍與需要人工介入的地方。保留來源可用性，並寫明窗口截止前採取回復或在新環境修復的條件。

## 維護窗口中的關卡

| 關卡 | 動作 | 進入下一步所需的證據 |
| --- | --- | --- |
| 維護就緒 | 依選定方式限制使用者操作，準備承接外部事件 | 新舊入口的行為符合預期；舊路徑即使仍被命中，也無法繞過必要的寫入限制 |
| 停寫成立 | 停止或排空全部寫入者，處理在途交易與工作 | 程序、寫入控制與待處理狀態相符；不是只看到某個副本數或一次零連線 |
| 最終資料就緒 | 在停寫條件持續成立時，取得最終資料與傳輸校驗資料 | 快照或同步邊界可確認，資料範圍明確；沒有未納入的新增來源寫入 |
| 還原完成 | 在目標受控狀態中恢復資料與必要服務 | 結構、資料與附件的驗證達到預定範圍；差異已解釋或處理 |
| 開放前確認 | 檢查入口、應用行為、排程與工作權責 | 目標驗證通過，來源仍受控，回復界線與操作角色已明確 |
| 受控開放 | 切換至目標服務並啟用預定工作 | 記錄目標開始接受寫入的邊界；只有預定的消費者與排程有執行權責 |
| 觀察與交接 | 完成使用者流程、背景結果、監測與備份檢查 | 已完成與待觀察項目分開記錄；異常有負責角色與處置方式 |

外部維護頁可以設在來源、目標或其他入口。停寫保證應由實際寫入來源的控制建立。DNS 快取與較早建立的連線需要另外處理，不能只憑新解析結果放行。[DNS 快取機制](https://datatracker.ietf.org/doc/html/rfc1034#section-3.6)

如果資料比對失敗、停寫條件失效或超出約定時間，停止後續開放。依計畫保留維護狀態，重新取得資料、修正問題或恢復來源。不要在資料新舊未釐清前同時開放兩邊寫入。

## 回復以資料狀態為分界

**目標尚未接受新寫入：**確認沒有目標測試或背景動作產生必須保留的變更，依計畫恢復來源的服務、工作權責與入口，再重新驗證。恢復期間也要避免兩邊同時處理同一工作。

**目標已接受新寫入：**先控制新的變動、保留目標資料與待處理狀態，再選擇已驗證的反向同步、重新搬移或在目標修復。未先同步必要資料，不得將舊來源當成可立即接手的最新系統。

**已發生外部動作：**另外確認該動作是否可撤回、查詢或補償。資料庫還原不會自動撤銷已送出的通知或外部操作；重新執行可能造成重複效果。

這個分界也見於 [AWS 搬遷回復指引](https://docs.aws.amazon.com/prescriptive-guidance/latest/best-practices-migration-cutover/cutover-stage.html#rollback)。文件提供的是決策參考，實際回復可行性仍須在目標系統驗證。

## 環境設定與憑證輪替

環境變數可能同時承載一般設定、服務存取憑證與加密金鑰。一般設定要核對目標環境的正確性；需要 rotate 的是敏感憑證或金鑰，不能把所有變數都隨機換值。盤點可存於私有工作區，公開文件不列實際變數名稱或值。

把舊主機、部署流程、背景工作與備份程序使用的憑證一併納入。優先檢查搬遷中曾複製、共用或交接的服務憑證，安排輪替與最小權限；臨時帳號、金鑰與不再需要的存取應撤銷。若疑似洩漏，立即依事件處理流程撤銷或替換，不能為了觀察期或回復方便而繼續信任它。[OWASP 憑證生命週期](https://cheatsheetseries.owasp.org/cheatsheets/Secrets_Management_Cheat_Sheet.html#27-secret-lifecycle)

對未疑似洩漏的服務存取憑證，可依供應商能力安排以下步驟：

1. 列出所有使用端，確認是否支援新舊憑證短暫並存；不支援時安排維護窗口與更新順序。
2. 建立新憑證並更新受控設定，讓網站、背景工作、排程與部署等相關使用端重新載入。
3. 透過實際連線或必要操作確認新憑證已生效，不只檢查設定檔已修改。
4. 撤銷舊憑證，確認舊存取已失效；同步修訂回復計畫，避免回復時仍依賴已撤銷的憑證。

Rails 的工作階段簽章與加密金鑰需另外評估。直接替換可能使既有登入、cookie 或簽章連結失效；用於持久資料加密的金鑰若直接移除，則可能無法解密舊資料或備份。依實際 Rails 版本與加密方式決定相容期、重新加密及舊金鑰保留條件，不假設每種加密方式都支援相同輪替流程。[Rails 工作階段與 cookie 安全](https://guides.rubyonrails.org/security.html#session-storage)、[資料加密金鑰輪替](https://guides.rubyonrails.org/active_record_encryption.html#rotating-keys)

## 舊環境退役條件

先確認觀察期結束、下一個相關排程與備份週期正常、還原能力已驗證、後續部署有人承接，且不再依賴舊環境回復。核對輪替與撤銷紀錄，關閉舊主機不代表它曾持有的憑證已失效。保留多久依業務與資料保存需求決定，不套用固定天數。刪除資源與撤銷存取另按既有授權執行。
