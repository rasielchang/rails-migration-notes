# Rails 搬遷計畫審閱

將經驗用在眼前的問題，幫使用者找出盲點與值得追問的地方。以使用者提供的計畫、程式或觀察結果為依據；分清楚已知事實、推測與尚待確認的資訊。

## 經驗與適用邊界

來源是 Rails 網站更換執行環境的經驗，聚焦可停寫的維護窗口。內容包含事後歸納，沒有涵蓋各 Rails 版本或部署方式的實測，也沒有完整的執行指令。

先確認本次工作是否符合這個情境。若涉及無停機、多地寫入、跨資料庫引擎或網域變更的 SEO 遷移，指出哪些設計超出本 skill 的範圍，不將參考流程當作已驗證方案。若使用者明確借用於其他框架，只將相關原則當作檢查問題，說明需要在該環境另行確認。

## 審閱時優先想這些事

| 原則 | 要追問的問題 |
| --- | --- |
| 最終資料需要明確邊界 | 備份或同步之後，舊站還會不會產生需要保留的新資料？ |
| 維護入口與停止寫入分開確認 | 網站、背景工作、排程、外部事件與在途操作，還有哪些可能寫入？DNS 切換本身不能證明已停寫。 |
| 文件與工具結果有證據範圍 | 現在的說法來自運行狀態、文件還是一般產品知識？查不到資源時，是否先確認了身分、範圍與權限？ |
| 備份存在只是第一步 | 是否確定能還原，且包含應保留的資料與附件？抽樣與全量驗證有沒有說清楚？ |
| 回復方式會隨資料狀態改變 | 新站若已接受寫入，回去之前如何保留這些變更？外部已發生的動作如何處理？ |
| 敏感憑證需要輪替與撤銷計畫 | 環境變數中哪些是一般設定、服務憑證或加密金鑰？哪些曾複製或共用，需要輪替？使用端更新、舊憑證撤銷及回復相依如何驗證？ |
| 驗收要跟到業務結果 | 畫面完成後，背景處理與外部結果是否也完成？避免因狀態尚未更新而直接重做操作。 |
| 費用與容量要一起討論 | 一般流量正常之外，哪些負載還沒觀察？降低資源後接受了哪些限制？ |
| 完成與未完成分開說 | 哪些有證據，哪些只是暫時沒觀察到問題？下一位維護者需要知道什麼？ |

只選與本次問題有關的項目，不要求使用者每次填完所有表格。指出計畫已有的合理安排，優先說明會改變決策的缺口。不要僅因同樣使用 Rails，就假設供應商、資料庫、工作系統或部署方式相同。

## 需要細節時再讀

- 討論停寫、切換順序或回復：讀 [切換與回復](references/cutover.md)。其中流程是參考情境，不能直接推定適用於無停機或多地寫入。
- 討論環境變數、憑證輪替或舊環境存取：讀[憑證輪替補充建議](references/cutover.md#環境設定與憑證輪替補充建議)。區分一般設定、服務存取憑證及加密金鑰；這是補充建議，不推定原案例已執行，也不把所有變數一律換值。
- 討論如何知道搬好了：讀 [驗證方法](references/verification.md)。不要把首頁能開推論為整條業務流程都通過。
- 使用者想帶走簡單提醒：使用 [搬家前後檢查表](assets/readiness.md)。
- 使用者需要較完整的工作文件：選用 [切換計畫](assets/cutover-plan.md)或[驗收紀錄](assets/acceptance.md)。

## 回答方式

先說最值得注意的幾件事，再解釋原因、目前證據與建議追問。資訊不足時明示假設；只追問會影響當前判斷的缺口，讓審閱結果聚焦使用者提供的計畫。

這個 skill 的預設工作是審閱與建議。正式環境操作依使用者另外提出的具體任務與既有授權處理，不從「檢查計畫」推定執行權限。實際搬遷仍需按目標環境驗證。

整理審閱結果時，區分已查證的事實、使用者的取捨與尚待驗證的建議，不補造對話或成效。需要對外提供摘要時，移除組織、人名、網域、位址、資源識別碼、變數名稱與值、私有路徑、實際日期、費用、業務數據及原始操作輸出。
